# Tasks

Work on one task at a time: local tasks or issues from GitHub, GitLab, Codeberg, YouTrack, Jira Cloud, Trello, Lighthouse Cloud, FogBugz Cloud, self-hosted Redmine/MantisBT or user-declared generic REST trackers. With Git, each task can have its own branch and shelved changes; switching back reopens its files. MIT; see `LICENSE`.

## Tool window

The native **Tasks** tool window shows grouped task/closed/issue trees with counts, active-task and elapsed-time details. The native toolbar follows the standard Tasks & Contexts flow: **New Task…**, selection-aware **Open Task… / Switch Task / Reopen Task**, **Close Active Task…**, **Search Issues…**, **Contexts…**, selected **Task Actions…** and **Update Issues**. Open operates directly on an existing row selection and only opens a picker when no task is selected; the active task disables Open, while Close Active always reviews the active task regardless of another selection. Open/Close forms show the reviewed task as a read-only value above their branch/issue choices and remember their last choices. Task Actions offers description, edit, switch, close, browser and work-time actions for the selection; Contexts offers save/load/remove. Open Task uses a native searchable picker; task descriptions open read-only native content tabs. The panel has no packaged web frame. Native text fields commit on blur/Enter. This is the supported interaction, not a pixel-for-pixel reproduction; generic server connectors, changelists, automatic context-on-commit, complete layout/bookmark/breakpoint restoration and full time-tracking UI remain outside the panel.

## Git integration (`process:git`)

Each new task gets a branch (`branchNameFormat`), checked out when you switch to it. Changes are shelved as stashes. Closing a task can merge its branch into the base branch and delete it. The commit message can also go to `commit.template`. Git failures retain a warning/local-activation behavior; there is no transaction across Git and task storage.

## Contexts (`events`)

Switching back to a task reopens the last 10 files opened while it was active. Named contexts can additionally capture up to ten currently open project editors in the invoking window (API 1.4); saving requires optional `editor.read`, foreign/nested-project editors are excluded and more than ten owned tabs refuse rather than truncate. The active editor's first selection is saved and restored only while its coordinates still fit the current file. Legacy named contexts and automatic task-switch file history are file-only and reopen at line/column zero; tab/split order, folds, dirty buffer contents, bookmarks and debugger breakpoints are not captured. No editor is closed, rewritten or silently saved by reopening. Reopening checks all recorded paths against the current owner before opening any and reports how many files opened; changed context state during a picker or a nested project created under recorded paths refuses reopening.

## Commands and status bar

- **Tasks: Close Active Task** (⌥⇧W, with the Close form's last choices), **Tasks: Open Active Task in Browser** (⌥⇧B), **Tasks: Copy Commit Message**, **Tasks: Update Issues**, **Tasks: Switch Task**, **Tasks: Save/Load/Remove Context**, **Tasks: Add/Remove Repository**.
- Status bar: the active task, window-scoped so each view reports its own root's active task. Click it to copy its commit message (`commitMessageFormat`, default `{id} {summary}`).

**Tasks: Apply Active Task to Commit Message** (also above Commit's message field; optional `vcs.read` and `vcs.write`) uses the active task's message format and previews the current/replacement text, task, project and draft revision. Cancel preserves the draft; changed task text or a changed commit revision refuses the write without retrying. It stages or commits nothing, requires included changes all within the task project, and refuses empty drafts and mixed-project selection. The host may save included dirty files when reading the pending draft, as its Commit workflow does. This is message-field integration only — no automatic task-close commit workflow, commit/merge choices or changelist commits.

## Trackers

GitHub, gitlab.com, codeberg.org, YouTrack Cloud, Jira Cloud, Trello and Lighthouse Cloud are used once their token is set in Settings › Plugins › Tasks; issues are updated every 20 minutes (open-only for automatic refresh). Closing a task can resolve GitHub, GitLab, Codeberg, YouTrack and Jira issues; work time can be posted to YouTrack and Jira. Tracker results retain plain descriptions (Jira Cloud descriptions are flattened from Atlassian Document Format to plaintext; formatting marks, links and embedded resources are not executed or fetched), bounded to 32 KiB with explicit truncation markers; hover shows a bounded escaped excerpt. These are cached server snapshots, not live status guarantees.

Setting **Include closed GitHub, GitLab and Codeberg issues in Search Issues** (`searchClosedIssues`, default off) includes resolved issues in explicit server searches; changing it invalidates the active search ownership signature so cached pages cannot be reused. YouTrack and Jira keep their configured native query semantics. Selecting a closed hit creates/activates a local task; it does not reopen the remote issue.

**Lighthouse Cloud**: configure `lighthouseHost` (e.g. `acme.lighthouseapp.com`), a positive numeric `lighthouseProject` and the `lighthouse-token` secret; grant optional `net:*.lighthouseapp.com`. The token is sent only through `X-LighthouseToken`; every request stays bound to that tenant/project. IDs use `LH-<tenant>-<project>-<number>`. Close Task can set the documented `resolved` state after rechecking tenant/project and exact API/web paths. Responses are capped at 1 MiB / 50 tickets; malformed, foreign-project and incomplete XML pages, including DTDs, are refused; no external XML entities are resolved and raw error bodies are not logged.

**FogBugz Cloud**: configure `fogbugzHost` (exact tenant such as `acme.fogbugz.com`) and `fogbugzProfile` (absolute path of an externally provisioned private JSON profile; owned regular 0600 file, no symlinks) and approve the Python 3 transport (`process:python3`). The token stays inside the helper; native settings/storage receive only an opaque profile fingerprint, issue number and latest-event identity. Each explicit search reviews the tenant/profile/query and admits at most 50 validated results; the XML API has no offset, so refine a larger query. Startup and periodic refresh never launch the credential helper. Close Task offers remote state update only for a validated closable issue: the helper freshly checks permissions and event identity, submits optimistic `ixBugEvent` and verifies closed state; TLS verification is mandatory, every redirect is refused, and a timed-out mutation requires checking the remote issue before retrying. See [profile setup and transport contract](adapters/README.md).

**Self-hosted Redmine and MantisBT**: add up to 16 nonsecret `selfHostedProfiles` descriptors (`family`, exact HTTPS `baseUrl`, absolute `profilePath`); the external owned 0600 profile contains the API key and optional explicit close-status ID — no API key enters native settings/storage. Search Issues offers those servers with documented filter parameters and up to five 50-result pages; Redmine uses server status metadata and offset/limit, Mantis requires a project and reads its status/workflow metadata; neither invents free-text or closed-state semantics when required metadata is unavailable. Close Task reviews the exact installation/project/issue/target status and stored profile/revision: Redmine freshly checks allowed closed statuses before PUT and verifies the result; Mantis verifies a strong ETag and uses `If-Match` for PATCH. Both recheck credentials and current revision, refuse foreign identities, verify the returned closed state, and never retry failed/uncertain writes automatically. Multiple installations under different URL prefixes retain distinct task identities. See [setup and server contracts](adapters/SELF_HOSTED.md).

The `generic` family covers other REST trackers through a user-declared JSON-pointer or Java-regex contract: see [adapters/GENERIC.md](adapters/GENERIC.md). A self-hosted YouTrack host (any DNS name) works through the optional `net:ask` grant approved in the host dialog at first use; unattended refreshes report it as denied.

## Search Issues

**Tasks: Search Issues** asks for a query, then a configured server/repository when more than one is available; each request searches that selection only. GitHub, gitlab.com and Codeberg use one repository at a time (GitLab also supports its all-visible-issues selection); YouTrack/Jira use a configured Cloud tenant; Trello uses the configured account; unsupported or missing Cloud hosts are excluded. Repository paths, returned issue hosts and issue API endpoints are validated before a result can be selected.

The picker offers **Next page**, **Previous page**, **Retry this page from server**, **New search query** and, when relevant, **Choose another server / repository**; empty results and request errors have separate states, and Retry is explicit (no automatic retry or rate-limit loop). Cancel preserves the active task and its context. Picking a hit keeps the Open Task branch review, or activates directly when Git integration is off; an existing task with the same ID can be reused only when tracker and issue API identity match.

GitHub/GitLab/Codeberg use `page`; YouTrack uses `$skip`/`$top`; Trello uses zero-based `cards_page`. Each page contains at most 50 issues, with a five-page limit per query/selection — a deliberate partial-results bound, not exhaustive search. Next is offered after a full page, so the following page may be empty. Jira enhanced-JQL search follows its opaque `nextPageToken`, including short/empty pages with a continuation. Prefix a Jira search with `jql:` to send your own JQL (at most 256 bytes, balanced quotes/parentheses, no trailing `and`/`or`/`not`, at most one final `ORDER BY field [ASC|DESC], …`); field and operator names are left for Jira to judge, and without the prefix the text becomes `text ~ "…"`. Jira search errors show a bounded constant reason, without raw server bodies or continuation tokens. The Trello member-card Refresh listing is separate; only an explicit search query uses these pages.

Previous pages use a memory cache keyed by project, server/filter configuration, repository, query and page: labelled, expiring after 120 seconds, holding at most 20 pages / 1000 issues; Retry invalidates that query/selection's pages and a new invocation clears the cache; nothing is persisted. The host exposes secret presence, not credential identity — a same-name credential rotation while a picker is open cannot be detected; retry or restart the search after changing accounts. Project/configuration membership is checked after each request and prompt, including immediately before accepting a hit. Queries are limited to 256 bytes, selections to 16, picker actions to 20 per invocation, and tracker response bodies to 1 MiB. Network timeouts/cancellation remain the host's responsibility.

## Cached issue references

After an explicit Search Issues, hovering an exact known issue ID in source shows its escaped summary, tracker and page URL, labelled as a cached search snapshot. The provider uses only validated in-memory search pages and the document's verified project identity: no storage/file reads, source searches, git commands, tracker requests or credential lookups occur on hover. Exact browser/API/source identity is verified per tracker (GitLab additionally requires response `references.full`, numeric project ID and IID to agree with the selected repository; Trello requires a 24-hex card ID plus 8-character shortLink agreeing with its response URL, contextual links use `https://trello.com/c/<shortLink>`). Missing/conflicting mappings, embedded Unicode identifiers, unknown IDs, expired results and same-ID/different-server collisions remain quiet. Only the last explicit search session is eligible; persisted/local tasks and background refresh results are not inferred into this cache, and these typed reference facts are excluded from task serialization. Snapshots are never presented as current authorization or live status; authenticated account identity is not available.

**Tasks: Open Cached Issue at Caret in Browser** and **Tasks: Activate Cached Issue at Caret Locally (No VCS Changes)** (optional `editor.read`) require one caret or one exact ID selection, current source text/version, the same owning project, an unexpired unambiguous hit and unchanged configuration. Local activation previews the exact root, issue, tracker, identity and scope, rechecks ownership after confirmation, refuses conflicting existing task identities, and updates local task/time tracking only — it bypasses the git/remote-state/context-reopening flow. Opening uses the previously validated HTTPS issue page with no new HTTP request. The source document is limited to 512 KiB and the exact ASCII issue token to 128 bytes.

**Tasks: Review Cached Issue Activation and Branch Options at Caret** opens the existing task/VCS options form for a not-yet-local cached issue when `process:git` is enabled; preparing or cancelling it changes no state and runs no Git. It binds the exact source text/version, project, issue identity, search expiry/configuration and branch-name format; Open Task rechecks these before importing/activating. The form shows the derived branch name; branch creation can be disabled and shelving selected explicitly. Existing branches are switched to; otherwise Git creates from HEAD.

## Stored task state

Task lists, active task/clock fields, choices, repository overrides and named file contexts persist under the exact concrete project-root key with a schema/owner/revision envelope. Malformed, foreign-owner or unsupported records never fall back silently to a default; valid legacy records are validated (including owned file paths) and upgraded on the next successful write. Empty task arrays, unknown identities, duplicate IDs, foreign/traversal file paths and unsupported sizes fail without replacing the stored bytes; storage denial does not create volatile replacement state. Different project roots keep separate counters and data. Read and write share a 2 MiB serialized bound; record limits are 512 tasks, 1000 cached issues, 64 named contexts, ten recorded files per task/context and bounded names/descriptions/overrides. A rejected oversized write retains the last valid record; writes recheck the original raw record and advance a checked revision, so stale writers fail instead of retrying — the SDK has no atomic compare-and-set, so a final read/write race remains. **Tasks: Reset This Project's Task State (Asks First)…** is explicit recovery for corrupt or unwanted records: it previews the exact key, byte count and deletion scope, rechecks the original bytes, then replaces only that key with a fresh owned default; it changes no git, tracker, source files or other project's key.

Rendered tree keys, field keys and button IDs carry opaque project/snapshot/form identity; only an exact local write confirmation can advance a callback binding, so stale callbacks cannot submit a previous project's form or target a replaced storage snapshot. UI drafts and selection are reset across projects; only submitted state is persistent. File-open events record only exact owning-project paths (with a longest-root check for nested projects). Active clock fields survive restart as elapsed wall-clock task time (including inactive time), not measured focused coding time.

## Permissions

| Permission | Used for | Without it |
|---|---|---|
| `project.read`, `storage` (required) | Read the project, keep task contexts and settings | The plugin does not load |
| `secrets` (optional) | Store each tracker's API token (`github-token`, `gitlab-token`, `forgejo-token`, `youtrack-token`, `lighthouse-token` and so on) in the IDE's secrets store. The plugin never logs a token; the host puts it in the request header | Trackers that need a token cannot be used |
| `net:api.github.com`, `net:gitlab.com`, `net:codeberg.org`, `net:*.youtrack.cloud`, `net:*.atlassian.net`, `net:api.trello.com`, `net:*.lighthouseapp.com`, `net:ask` (optional) | Fetch and update issues on the trackers you configure; only the hosts of the trackers you turn on are contacted. `net:ask` covers a self-hosted YouTrack host you configure | That tracker is unavailable; the others still work |
| `process:git` (optional) | A branch per task, shelving, merge on close, commit template | Tasks work without VCS integration |
| `process:python3` (optional) | The FogBugz Cloud and self-hosted Redmine/MantisBT/generic credential-profile transports | Those trackers are unavailable |
| `vcs.read`, `vcs.write`, `events`, `clipboard`, `editor.read` (optional) | Detect the project's remote, apply the commit message, record the files of each task, Copy Commit Message, cached issue caret actions | Those features are off |
