# Spring Data Tools

Spring Data repository support for Java and Kotlin projects in OpenIDEA.
MIT; see `LICENSE`.

## Checks

- **Derived query checks**: repository methods without `@Query`/`@NativeQuery`/`@Procedure` are parsed the way Spring Data parses them (`find|read|get|query|search|stream|count|exists|delete|remove` … `By`, criteria split on `And`/`Or`, operator keywords, `IgnoreCase`/`AllIgnoreCase`, `OrderBy … Asc|Desc`). Each property path is resolved on the domain class (longest camel-case prefix first, `_` as explicit separator, nested types, collections unwrapped): an unknown property is a warning at that part of the name. The criteria must take as many arguments as the method declares (`Between` 2, `IsNull`/`True`/`Empty`… 0, others 1; `Pageable`, `Sort`, `Limit`, `ScrollPosition`, `Class` don't count).
- **`@Query` checks**: a warning on a `:name` parameter that no method parameter binds (by `@Param("name")` or by the parameter name), and on `@Modifying` without `@Query`. In JPQL/HQL queries (not `nativeQuery = true`, not concatenated strings): a warning on an entity name after `from`/`join`/`update` that looks like a typo of a project entity or class (other unknown names stay quiet: they may come from a library or `orm.xml`; `from` inside functions such as `extract(year from d)` is not a declaration), and on `alias.property` paths (`u.address.city`) naming no property of a project entity; library types stay quiet.
- **MongoDB**: in a `@Query` of a repository file that imports `org.springframework.data.mongodb`, a warning (`mongo-unknown-field`) on a top-level key whose first path segment is no property of the domain class (nor `id`, `_id`, a `$` operator or a `@Field`/`@Column`/`@JsonProperty` name). Nested documents are not followed; a domain class with a library superclass is not checked.
- **JDBC checks**: namespace-guarded local `@Sequence` and `@MappedCollection` checks are live under `springData.checkJdbcMapping`.
- **Type compatibility checks**: parameter and return type findings are not reported until qualified library/source types can be established.
- **Projection checks**: closed interface projection getters, record DTO components and literal `@EntityGraph` attributePaths are checked against the fully scanned in-project entity property tree (warning only when provable, Info for clear type conflicts); nested derived-query paths follow the documented whole-name-then-right-to-left split with underscore traversal.

## Completion, navigation, hover and inlays

- **Completion** of derived query names: after `findBy`, `countBy`, `findAllByNameAnd`… the entity's properties (and nested ones one level deep), then operator keywords, `And`/`Or`/`OrderBy`, `Asc`/`Desc`. Each proposed direct/nested spelling must resolve back to its intended property chain: a direct `addressZipCode` wins over `address.zipCode`; the nested alternative becomes `Address_ZipCode`; the first existing longest camel-case head commits even when its tail fails. Leading/doubled underscores, acronym edge cases, expanded Unicode capitalization and ambiguous source members are supported only when the spelling round-trips (the [Spring Data Commons 3.5 property-expression contract](https://docs.spring.io/spring-data/commons/reference/3.5/repositories/query-methods-details.html)). Suggestions are capped at 512; declared/native/dynamic queries, comments, strings and default method bodies do not receive derived-name suggestions. JPQL field completion requires an explicitly owned JPA `Query`, literal unescaped source and known alias/type links.
- **Navigation**: a gutter arrow on the repository opens its domain class (and `<Repository>Impl` when there is one); Go to Definition on a property part of a method name opens the field, preserving actual declaration ranges including UTF-16 offsets (getter ranges remain navigation targets rather than replaceable field tokens).
- **Derived query tooltip**: a gutter marker on each derived query method that reads the name in words (`find User where first name and last name, order by age desc`). Derived-method hover describes a query only after every property part resolves to cached source.
- **Named-query hints**: hover over an explicitly owned literal JPA Query annotation counts the current query names and matching explicit aliases; parameter inlays show the criterion associated by the known derived-argument order (two-argument/unknown operators get no speculative labels) and show explicit literal `@Param` aliases which also occur as named placeholders in that query (repeated placeholder use yields one hint per bound declaration). Only abstract source methods, known current project domain models, the existing `checkQueryTypes` switch and unescaped literal query values up to 4,096 bytes are admitted; native/dynamic/ambiguous/foreign forms stay quiet. These are source declaration hints, not call-site SQL bindings, query plans, inferred database types or runtime results.
- **Identifier hover**: over a known cached domain match, a repository identifier hover shows the declared domain and a bounded escaped source path/line, and distinguishes complete-within-cache from incomplete/stale positive inventories. It never infers the persistence identifier type, custom base semantics or effective runtime activation; stale/foreign owners, cold/unknown domains and disabled hints stay quiet.
- **Show Repository Inherited Members** (command and editor context menu): lists the members a repository inherits from Spring Data's own interfaces (`CrudRepository`, `ListCrudRepository`, `PagingAndSortingRepository`, `JpaRepository`, `MongoRepository`, `QueryByExampleExecutor`, `JpaSpecificationExecutor`, reactive ones); custom parent interfaces are not expanded. Available in Java and Kotlin files.

## Generation

- **`repository` snippet**: typing `repo` at the top level of a Java or Kotlin file offers a repository interface skeleton.
- **File template**: Spring Data Repository (Java and Kotlin) in the New File menu.
- **Sort the query fields** (code action in a MongoDB `@Query` string): orders the top-level fields of the filter document alphabetically (nested documents are kept as written; the `sort` attribute is never reordered because its order matters).
- **Generate CrudRepository** (`**Generate CrudRepository for …**` on a supported top-level entity): previews a new Java/Kotlin interface in the same package folder; the host creates and opens it as one atomic, undoable FileAction with overwrite disabled.
- **Generate JpaRepository**: an additional FileAction for proved source-local JPA entities, alongside the common CrudRepository one, using the qualified Spring Data JPA interface with the proved domain and scalar ID types. MongoDB and JDBC entities keep the common CrudRepository action only.
- **Generate IdentifierProjection**: a closed interface projection for the proved scalar identifier property, using its actual field/record/getter property name and boxed type. Java getters and Kotlin read-only properties are supported.
- **Generate InterfaceProjection**: select several admitted current-source scalar properties for a closed interface projection. Java fields, record components and plain bean getters are supported; Kotlin constructor/body properties retain source nullability. Unknown, transient, static or conflicting properties are omitted; explicit access overrides and inherited entity layouts stay outside the model. Names must come from the displayed source list; duplicates and nested/transformed paths are rejected.
- **Generate JpaRepositoryWithEntityGraph**: a new JPA repository with a `findById` override annotated with selected direct source association paths. Only canonical JPA association/embedded/element-collection annotations establish offered paths; unknown namespaces, transient/static members, explicit access overrides and arbitrary nested paths do not manufacture graph attributes. Does not mutate an existing repository or infer library graphs.
- **Generate JpaRepositoryWithFinder** (also **WithPagedFinder**, returning Page with an explicit Pageable parameter, and **WithSortedFinder**, returning List with Sort): a new repository with a reviewed finder using up to eight selected direct source properties joined with `And`. Enter property names for equality, or `property:Operator`. All scalars support Equals, Not, In, NotIn, IsNull and IsNotNull; String supports Like, NotLike, Containing, StartingWith and EndingWith; known numeric types support comparison operators and Between; Boolean supports True and False. The complete method is checked against the derived-query grammar, preserving argument counts and actual property boundaries; In/NotIn emit Collection parameters, Between emits lower/upper parameters. Nested or underscore paths, repeated properties and unsupported type/operator combinations are withheld. Property casing must survive JavaBeans capitalization/decapitalization unchanged (ordinary camel names and acronyms such as URL are admitted; Name/aB-style ambiguous spellings are withheld). Generated parameter names avoid collisions; Java and Kotlin retain source types.
- **Add finder to existing JpaRepository**: inserts a reviewed List-returning finder into a same-package, same-language existing interface with one exact fully qualified JpaRepository parent for the current source entity and identifier. Explicit interface bodies only; generic/custom parents, wildcard/foreign domain imports, Kotlin aliases and duplicate method names are refused. Existing content and CRLF are preserved; source and target snapshots are rechecked before the atomic edit; cancellation returns no edit.

## How it works

A repository is an interface extending a `…Repository`/`…RepositoryBase` type with type arguments (the first is the domain type) or annotated `@RepositoryDefinition(domainClass = …)`. Properties are the non-static, non-transient fields (not `@Transient`) and record components of the domain class and its superclasses. Matching is text-based, by simple type name among the project's Java and Kotlin sources: when the domain class, a superclass or a traversed type isn't a project class (a library type), nothing is reported.

Live providers use the supplied Java/Kotlin document version and a bounded source cache warmed during activation and optional file events. Diagnostics, hover, inlays and gutter markers perform no project scan or file read and no manual diagnostic publication; unsaved current-source snapshots replace their cached entry. Absence checks and query hints require fresh, complete, unambiguous project facts; cold, malformed, oversized, conflicting or stale facts stay quiet. Inputs are limited to 128 KiB, cached source files to 256 type / 2,048 member declarations, model construction to 5,000 class names, diagnostics to 500 and inlays to 200.

The live repository subset requires an explicitly imported known Spring Data base (`Repository`, `CrudRepository`, `ListCrudRepository`, `PagingAndSortingRepository`, `JpaRepository`, `MongoRepository`, `ReactiveCrudRepository`), with no local/conflicting import shadow. Query/NativeQuery/Modifying/Param annotations require an exact supported fully qualified spelling or one unambiguous explicit framework import for the simple spelling: each spelling passes an independent exact FQN or unique simple-import check, so a foreign `@other.Query` cannot borrow a separate Spring Query import, multiple supported imports are not one identity, and a qualified `org` root shadow is rejected; foreign or ambiguous annotations suppress the method rather than invent query facts. The same exact admission applies to the source-local JDBC `@Sequence`/`@MappedCollection` field and record/constructor-component checks; unknown annotation identities leave their property declarations available to the cached source model. Domain classes must have a unique qualified source owner visible from the repository package or an exact import; association/supertype links use their declaring source package/imports, and unrelated same-simple-name classes do not compete. Unknown/library, alias, generic-hierarchy and ambiguous owners stay quiet; dynamic/concatenated query strings remain quiet. Custom repository bases and wildcard-import-only ownership remain outside the completion/navigation/live subset.

A nongeneric interface using an explicitly imported or fully qualified `org.springframework.data.repository.RepositoryDefinition` is supported when its sole annotation supplies exactly one simple Java `.class` or Kotlin `::class` literal for each of `domainClass` and `idClass`, with no competing base interface; domain ownership still comes from the same unique qualified project-source cache, never the annotation spelling alone. Aliases, constants, qualified domain literals, duplicate/unknown attributes and ambiguous or cold domains stay quiet; `idClass` is a declared literal shape, not an inferred persistence ID/type claim.

Every cached model source is rechecked against the current innermost open-project root before publishing derived/query completion, definition, markers, hover, inlays or model diagnostics: one bounded root inventory (64 projects maximum) replaces stale lexical parent ownership without source discovery or file reads in editor requests, so opening a nested project cannot leave its previously cached classes available to the outer repository. Unknown/invalid/oversized root inventories withhold model facts; excluded sources make model completeness false, so absence checks and completeness-dependent hints stay quiet, while known unaffected outer properties still supply positive completion/navigation. Canonical absolute source/root paths and project boundaries are required.

Standard container traversal in completion requires a proven explicit standard-container import; custom or unproved generic containers do not manufacture element properties. `springData.checkQueryTypes` controls the derived-query hover and criterion hints.

Repository generation uses current source facts only: explicitly imported or fully qualified `jakarta.persistence.Entity` / `javax.persistence.Entity`, MongoDB `Document`, or relational `Table`, with exactly one locally declared ID from the matching persistence namespace. Fields, Java record components, no-argument getters and Kotlin primary-constructor properties are supported. Known scalar identifier types are boxed for Java and mapped to Kotlin built-ins; UUID and BigInteger are supported when their namespace is explicit; there is no assumed `Long` fallback. Nested/generic/inherited entities, composite/embedded IDs, unknown custom identifier types, wildcard/aliased annotation identity and ambiguous facts do not offer the action. The package must be a named Java/Kotlin package matching the source folder; generation stays in that folder and accepts a new ASCII interface name bounded to 128 bytes. Source snapshots are bounded to 128 KiB; at most four pending actions are retained. Resolution verifies the exact document path, language, version and text, project identity, and the current dirty-aware source text before and after the concrete confirmation. Existing Java or Kotlin targets and other top-level types in the target folder are rejected; collision discovery is bounded to 64 files per language, 128 KiB per file and two seconds per pass, and incomplete or unreadable checks refuse creation. The host additionally confines paths, checks the document version during resolution, and rejects a target that appears before atomic application. Existing source buffers are never edited; no external writer, process, network request or direct project write is used.

## Query injections

API 1.4 query injections cover owned contiguous Java/Kotlin JPA Query
value/countQuery literals and NativeQuery annotations. Native queries use SQL;
non-native queries use the JPQL language supplied by JPA Assist. Escaped,
concatenated, interpolated and dynamic source stays outside physical mapping.
Physical routing is separate from type-aware query analysis: the released
embedded-color renderer loads only built-in CodeMirror grammars and does not
consume plugin SyntaxProvider tokens for injected spans, so native embedded
JPQL coloring remains a host-renderer gap, while source-model query
completion/diagnostics and physical provider routing remain independently
usable.

## Not implemented

- Complete typed query-language tooling and a preview of the resolved query; effective classpath and library types; classpath metadata; custom store/query-provider semantics.
- Cross-root `jdbc-shared-entity` findings (until qualified aggregate ownership is modeled); the previous parser remains tested.
- Geo `Near`/`Within` arguments aren't counted; nested MongoDB documents aren't followed; navigation to repository fragments other than `<Repository>Impl`.
- Semantic usages/Rename: no field anchors or indexing export are registered, since getter spellings, transformed derived fragments, external repositories/queries and runtime mappings do not form a proven complete same-spelling rename set.
- ORM/PSI services: selecting an arbitrary base repository class, target directory or ORM model entity, resolving library classpath availability or cross-source-root package/type collisions (static file templates remain available for manual cases).
