# Spring Structure Tools (aritti.spring-integration)

One **Spring Structure** tool window (right) with four sections, plus the editor support of three former plugins: Spring Integration (this one), Spring Batch and Spring Modulith. `aritti.spring-batch` and `aritti.spring-modulith` are no longer maintained: uninstall them, otherwise their windows and completions show twice.

- **Channels**: the Integration Channels diagram described below.
- **Batch**: Spring Batch jobs, steps, flows, splits and decisions as a diagram. XML job navigation, completion and transition/bean checks, `spring.batch.job.name` navigation, `jobParameters` key completion, late-binding scope checks, Spring Batch migration hints (setting `springBatch.checkChunk`).
- **Modules**: Spring Modulith application modules with named interfaces, allowed and actual dependencies; checks for internal types and unlisted dependencies, `allowedDependencies` completion, quick fix to make a module open.
- **Diagram**: the module dependency diagram; the command "Spring Modulith: Copy Module Diagram (PlantUML)" copies it.

Source editor sections are gated by dependencies in the root build file (`spring-integration`, `spring-batch`, `spring-modulith`; multi-module builds and version catalogs count as unsure). Explicitly configured Batch runtime profiles instead use their validated artifact/classpath contract. The command ids and storage keys of the absorbed modules are prefixed `batch.` and `modulith.`; their old settings values are not migrated.

## Spring Integration channels

Spring Integration message channels for Java, supported Kotlin annotations and XML configuration:

- **Channel index**: channels come from explicitly owned `@Bean` methods returning Spring `MessageChannel`, `PollableChannel` or `SubscribableChannel`, `MessageChannels.direct/queue/publishSubscribe/executor/flux/priority/rendezvous("x")`, the supported contiguous DSL's `.channel("x")`, and `<int:channel id>` / `<int:publish-subscribe-channel id>` in any integration namespace. A Java/Kotlin Bean source counts as a channel declaration only when its Bean annotation and channel return type have exact explicit Spring ownership; a type name ending in `Channel` is insufficient. DSL facts require explicit Spring `IntegrationFlow(s)`/`MessageChannels` factory ownership; only direct contiguous proved from-to-channel chains establish string channel steps.
- **Endpoints**: `@ServiceActivator`, `@Transformer`, `@Filter`, `@Router`, `@Splitter`, `@Aggregator`, `@BridgeFrom`, `@BridgeTo`, `@InboundChannelAdapter`, `@Publisher`, `@MessagingGateway`, `@Gateway` channel attributes, `IntegrationFlow.from("x")`, and the XML `input-channel`, `output-channel`, `channel`, `request-channel`, `reply-channel`, `default-request-channel`, `default-reply-channel`, `discard-channel`, `error-channel` attributes. Each is read as consuming or producing (`input-channel`, `replyChannel` and the `channel` of an outbound adapter consume; `outputChannel`, `requestChannel`, `discardChannel` produce).
- **Go to Definition** on a channel name opens its declarations, or the endpoints consuming it when nothing declares it (Spring Integration creates input channels on demand). On an XML `ref` it opens the bean (XML `<bean id>` or a Java/Kotlin bean name).
- **Completion** of known channel names, and of bean names in `ref`.
- **Gutter arrows**: a consuming endpoint points to the producers sending to its channel, a producing one to the consumers.
- **Warnings**: an output-side channel (annotation or XML) that no endpoint consumes and no bean declares; a `ref` to a bean the project doesn't declare. Input channels, DSL channels, `${…}`/`#{…}` names and common infrastructure beans (`errorChannel`, `nullChannel`, `transactionManager`…) are never reported, and nothing is reported until the first full scan of the project. Uncertainty from unproved registrations withholds the negative warnings.

Matching is text-based, by channel name as written in string literals and attributes; constants (`outputChannel = Channels.OUT`) aren't followed. Beans and channels from libraries, auto-configuration or other modules aren't seen. Kotlin sources count for bean names and annotations; the Kotlin DSL doesn't. Channel/bean usages are narrowed to the file's context closure from literal `@Import(X.class)`, `@ImportResource("classpath:x.xml")`, `@ComponentScan(basePackages)` and XML `<import resource>` edges (a bare `@ComponentScan`/`@SpringBootApplication` scans its own package and subpackages); `classpath:` maps to `src/main/resources`; placeholders, patterns, profiles/conditions, `@ComponentScans`, ImportSelector/ImportBeanDefinitionRegistrar imports, non-classpath `@ImportResource` paths and Kotlin edges are withheld. Unowned files and unprovable imports stay global; usages whose definitions sit in several unrelated contexts get a "defined in N contexts" info instead of picking one.

**Spring Integration: Current File Channel Occurrences** lists the supported literal channel declarations and references in the current unsaved XML document (caret on a supported ID/reference): source order, role, line and UTF-16 column, opening only a listed location in that same unchanged document. It requires one local channel declaration and refuses known competing bean, alias or core endpoint registrations; cancel, denied optional `editor.read`, stale source or project ownership produce no navigation. Java Go to Declaration and this picker use current-text, explicitly owned declarations and literal names, without a warmed project index.

On a channel ID or bridge reference in a simple XML channel/bridge document, **Rename literal channel in this document…** validates a unique new name and shows the complete before/after document before returning undoable edits. It also covers literal channel-valued attributes on flat service activator, transformer, filter, splitter and aggregator endpoints; handler `ref`/`method` values are preserved, and dynamic expressions, unsupported attributes or a handler reference colliding with the selected channel withhold the action. Imports, profiles, nested endpoints and competing registrations are excluded.

**Spring Integration: Find Channel Usages in XML Import Tree** follows literal relative imports and alias chains from the active XML root, then navigates exact physical occurrences; **Rename channel in this XML import tree…** returns one reviewed multi-file workspace edit, including alias targets while preserving alias names (renaming an alias declaration renames it and its direct users, preserving the underlying channel and other alias names). Admission is limited to 16 files / 256 KiB, supported flat channels/endpoints/aliases and one project; profiles, wildcards, classpath imports, nested endpoints and unresolved or colliding aliases are rejected.

## XML source navigation and generation

Current-text XML channel hover and Go to Declaration resolve a unique literal `channel` / `publish-subscribe-channel` ID directly below the same Spring Beans root, using the exact core Integration namespace; core bridge, service-activator, transformer, filter, splitter, aggregator, router, gateway, inbound/outbound-channel-adapter and chain channel attributes receive a local reference count and source declaration line. Supported tokens with no unique local declaration return no target instead of guessing a project-wide match; a same-file bean/endpoint ID or alias registering the same spelling suppresses navigation as ambiguous. DTDs, entities, escaped/whitespace names, nested profile blocks and unknown namespaces are excluded. The same bounds apply as hover overall: 32 KiB current text, 4,096 XML events, 256 tokens, a 10 ms parse budget; names are ASCII literals of at most 128 characters. Namespace admission uses a scoped namespace-aware reader: illegal `xml`/`xmlns` rebinding, aliases of reserved URIs, empty prefixed bindings and unbound used prefixes are withheld; legal `xml:lang` and ordinary shadowing remain supported. A file-local channel name cannot prove a complete Spring context owner, so no automatic host indexing, Find Usages or Rename anchors are published.

At a root-level caret in an existing Spring Beans XML source, **Create XML message channel…** asks for a literal channel ID and previews the complete exact resulting XML; Confirm returns one atomic same-file insertion, Cancel no edit. It reuses an existing root-declared prefix bound exactly to `http://www.springframework.org/schema/integration` and inserts a bare `<prefix:channel id="…"/>` before the validated Beans root close, adding no namespace/schema mapping and changing no endpoint. Channels without queue/priority/rendezvous/dispatcher configuration are treated as `DirectChannel`; `nullChannel` and `errorChannel` are named default channels and reserved. IDs are at most 128 ASCII bytes starting with a letter/underscore. The supported source is conventional well-formed unprefixed `<beans>` XML bounded to 12 KiB / 2,048 XML events; nested Beans/profile scopes, DTDs, entities and malformed XML are outside this subset. Resolution verifies source path/text/version and exact project root before and after prompts (at most eight single-use pending tokens); a fresh command-owned source inventory checks declared bean/channel names and aliases (bounded to 8 MiB scanned, 8,192 names / 1 MiB of name text, 512 KiB per file, a three-second pass) and refuses creation on collisions, dynamic names or an incomplete pass instead of treating unknown facts as absence.

**Link local XML channels with bridge…** at the same caret offers two unique, literal, self-closing bare `<prefix:channel id="…"/>` declarations directly under that root: pick the input channel, then the output (the input is excluded from the output picker because the bridge adds a consumer). Only this source's bare DirectChannel forms are candidates (at most 64); configured channels, duplicate IDs/aliases, expressions, imported/global channels and existing same-direction bridges are excluded. It returns one atomic insertion without applying it, preserving the existing prefix, LF/CRLF and Unicode; no direct writes, process, network or runtime operations occur. The action adds an endpoint; it does not infer effective context ownership, consumer ordering, imported aliases, whole-flow loops or polling, and generates no poller.

**Create DirectChannel configuration source…** offers a new sibling Java/Kotlin file from one source-owned `@Configuration` context with an explicit Integration import or qualified reference (the declared package must match the source folder). It creates one class with an explicit configuration bean name and one DirectChannel `@Bean` method using qualified framework names; Kotlin class/method are open. Existing files/directories, known package/bean/configuration IDs and namespace-root shadows are refused; constant/concatenated `@Bean`/stereotype names refuse the literal collision proof. Bounds: source/package/path 12 KiB / 512 bytes, identifiers ASCII 128 bytes maximum, the same bounded source inventory (1,024 owned paths, 512 KiB per file, 8 MiB total, three seconds, 8,192 IDs/names per 1 MiB), eight single-use in-memory intents. **Create and import DirectChannel configuration source…** creates the same file and adds one fully qualified Spring `Import` annotation to the existing Configuration in one FileAction (non-overwriting Create/Open plus one source Edit), only when no Import annotation, wildcard imports, generic/inherited configurations or namespace-root shadows are detected; it never merges existing Import arrays. Classpath availability, component-scan registration and effective runtime bean/type ownership are not resolved; the preview says so.

Java hover shows bounded positive facts for a supported source-owned Configuration containing explicit `@Bean` methods returning `MessageChannel` and literal `ServiceActivator` input/output references: the declaration line and current-file reference count on the exact method or literal bean name range. It requires one supported declaration without competing literal registrations; dynamic/compound/array/escaped names, custom/shadowed imports and generic or inherited configurations stay quiet. Documents over 12 KiB are out; at most 128 source tokens are retained. Configuration imports, composed annotations, subclasses and effective runtime context are not resolved.

## Spring Batch

XML job navigation, completion and transition/bean checks, `spring.batch.job.name` navigation, `jobParameters` key completion, late-binding scope checks and migration hints. Current XML `next`, transition `to` and stop `restart` requests are handled directly from their physical Batch job/flow scope: completion, navigation and hover require the exact Batch namespace, a supported attribute shape and a unique literal direct state declaration in that same job/flow; nested flow members keep their own scope, and missing/duplicate/foreign candidates do not fall back to another job, file or project. A single leading XML declaration is retained; declarations inside/after the root, duplicate declarations and declarations preceded by whitespace/comments are rejected for all local Batch navigation, completion, hover and link actions.

**Link Batch step next to a local state…** (caret on a step opening tag/ID, or inside an explicit `next` attribute) offers unique other direct states in the same physical source job/flow, shows the exact complete resulting XML, and returns one source Edit inserting a missing `next` attribute or replacing only its existing value; tasklet content and other attributes are unchanged. The source step, target and containing job/flow must be unambiguous source-owned forms without parent/abstract inheritance; a step with child next/end/fail/stop transitions, self, unchanged, duplicate and other-scope targets are excluded. If the full resulting XML doesn't fit the host's 16 KiB confirmation limit, resolution refuses before asking. Four single-use intents are kept.

**Rename Batch step in this document…** (also decision IDs) updates a unique literal direct step ID and every proved direct step/decision next, child next@to and stop@restart reference to it, in one flat physical XML job. The new ASCII ID cannot collide with document IDs, names, aliases or existing target literals; nested flows/splits/jobs, duplicate IDs, inherited/imported states and dynamic/encoded/foreign target roles refuse the action. It lists no edits until input and complete before/after review are approved, and returns one grouped FileAction edit without a direct write. Inventories are bounded to 32 KiB source, 512 elements / 256 attributes / 4,096 events / 64 edits. **Spring Batch: Find Step or Decision Usages in This Document** opens a read-only picker on the same model (declaration or a proved next/to/restart target), distinguishing declaration and reference kinds with full path, UTF-16 range, job/step and source version; it reads only the focused editor through optional `editor.read`, rechecks path/version/text/owner before navigating, and never edits source. Cross-file usages and global indexed Rename remain absent.

Batch source job/step names require an exact imported or fully qualified Spring builder constructor with an ordinary literal first argument; unproved builders suppress missing-job diagnostics. Parameter-adder facts require a contiguous chain from an exact Spring `JobParametersBuilder` constructor; late-binding parameter reads require an exact Spring `@Value` annotation with one ordinary complete literal expression on a parsed member or parameter (or a complete literal expression in an unqualified owned Batch bean-reference attribute or a standard top-level bean property/constructor-arg value); foreign annotations, comments, ordinary strings and compound/dynamic values cannot donate indexed completion keys. Bean references share Integration's exact annotation-origin and literal-name admission: foreign, compound, aliased or otherwise unproved source names cannot define tasklet/reader bean references or completions, and unknown-bean warnings are withheld there. Kotlin Batch parameter-key completion uses the owned source builder/expression model; Java-only migration and scope checks are withheld for Kotlin.

Batch XML checks distinguish top-level declarations from inline subjobs, partition steps and anonymous split flows; required IDs/flow parents and merge booleans follow the reviewed schema context. **Spring Batch XML compatibility** defaults to Auto (common checks only); explicitly selecting 5 or 6 enables version-specific migration diagnostics (compatibility 6 reports removed `throttle-limit`/subjob `job-launcher`, the replacement `job-operator`, and the XML namespace deprecation). Modern unversioned `spring-batch.xsd` URLs do not prove a runtime version; unknown explicit schema URLs suppress version assumptions. Additional operator/incrementer/extractor/handler/aggregator bean references participate in supported source navigation. `springBatch.checkChunk` controls the migration hints.

### Optional reviewed Batch CLI runtime

Configure `springBatch.runtimeProfile` as `runner-5.2.6` or `operator-6.0.6`, list explicit project-relative classpath directories/JARs (one per line), and select the exact compiled context plus its Java/Kotlin source; Runner also accepts an exact XML classpath resource and matching source. Profiles are disabled by default and require the optional approved `java` executable. **Validate Configured CLI Profile** inspects actual classpath artifacts without loading application code (pinned official core JAR, unique launcher/context, compiled binary name, runtime-selected multi-release entries, bounded fingerprints; manifest-added classpaths, escaping paths and shadowed launchers refused). **Run Reviewed Job Operation** shows the actual argv, cwd, source and artifact identity, validates again, then starts an owned process; Runner supports start/next/stop/restart/abandon, Operator also recover. Up to three launch processes leave a fourth slot for control requests. **Poll CLI Output** reads all owned sessions with bounded display output; **Cancel CLI Process** ends one selected local process and does not send a Batch stop; a detected project switch ends old owned CLI processes. **Inspect Execution Repository State** separately reviews context startup and queries an exact execution ID through the configured `JobExplorer`/`JobRepository` (job/instance/status/times and an observation time; an explicit point-in-time query, never automatic). Artifact fingerprints do not establish source build provenance or effective datasource identity; invoking the selected context includes its startup code and configured database connections.

## Spring Modulith

Application modules with named interfaces, allowed and actual dependencies. Checks for internal types and unlisted dependencies, `allowedDependencies` completion (including `module::*`; Go to Declaration on `allowedDependencies` navigates module declarations, named-interface packages/types and wildcard owners), and a quick fix to make a module open. Boundary diagnostics and dependency graphs include qualified project type names in explicit field declarations, `new`, `instanceof`, `extends`, `implements`, `throws`, annotations and class literals (also at use sites of types imported by exact single-type import that are module-internal or not in `allowedDependencies`); comments, strings, unknown types, wildcard/static imports, shadowed names and type parameters stay quiet. This is a source model: generic arguments, casts, nested types, arbitrary expression resolution and library types are not claimed.

On source refresh, declared module package directories receive native `O` (open) / `C` (closed) badges with explanatory tooltips, from the fresh admitted Java/Kotlin source model, requiring an existing directory in the owning project. On a proved cross-module internal-type import, **Expose imported type as a named interface…** offers a reviewed annotation edit to the unique public project type (fully qualified Spring annotation, imports/package/visibility preserved, existing annotations or shadowed qualifiers refused). For an implicit closed module with no package descriptor, **Open imported type's module…** previews a new fully qualified `@ApplicationModule(type = ...OPEN)` descriptor with a non-overwriting atomic file create. Kotlin application roots, declared types/imports and literal `@PackageInfo` metadata participate in the source model; unsupported aliases/constants/interpolation or conflicting metadata visibly mark the model incomplete and withhold negative boundary conclusions and badges. Creating an absent module package descriptor remains restricted to Java source roots.

## Diagrams

Channels, Batch and the Modulith **Diagram** section use one packaged SVG renderer. The Channels graph draws message channels as nodes (declared ones accented) and each endpoint as a small node, input channel -> endpoint -> output channel, from the project index; click a node to open its source, Refresh rescans. The DSL flow chain edges are not drawn (`.from("a").channel("b")` shows both channels but no endpoint node).

Each graph supports Zoom in/out/100% (50–200%), selected-node highlighting, plain read-only source facts (channel/endpoint or job/state or module candidate, source location, cached incoming/outgoing link counts), clear selection and guarded source Open: an exact node in the current project's graph, an owned source path and a matching reference in a bounded dirty-aware reread (512 KiB) before opening; forged paths and changed sources are refused. Zoom/selection belong to the concrete project root and reset on a project switch; a missing/denied owner renders a replacement empty message. Modulith keys include a losslessly encoded absolute source-path suffix, so identical logical module names in another project do not reuse a captured row identity. Presentation is capped at 512 nodes, 2,048 displayed edges, 4,096 candidate source records and 128 KiB of node-key text (16 KiB per key, 512/256-byte labels/details with truncation markers); caps or ownership exclusions mark the presentation partial, and displayed link counts never assert unseen relationships are absent. Rendering adds no process or network request.

## Live diagnostics and caches

The registered wrapper returns one versioned diagnostics result for the enabled Integration, Batch and Modulith checks; the Integration gutter arrows are retained and no second Problems producer is published; a current unsaved fix replaces only the matching findings in the combined result. The standalone Batch/Modulith plugins must be removed to avoid their separate producers.

Typing requests do not discover files or read build files; module/dependency applicability is cached from the root-build heuristics. Optional `events` warms those facts and bounded source passes on open/save/watched changes, with build changes invalidating cached applicability; navigation and views can also warm their indexes. A missing event grant or a cold instance can leave project-wide checks quiet until another supported interaction warms them. Local Batch checks use current text; cross-file absence and Modulith boundary checks require a complete source pass still within its 120-second trust interval. Unavailable, partial and expired evidence is quiet, not proof that every reference is valid. Live documents over 256 KiB are skipped; cached Modulith live models above 1,000 source files are conservatively omitted; each module's event warming has a 20 ms reading budget; file-change invalidation evicts all module caches; other projects warm independently and never reuse an anonymous root.

If file-saved/files-changed subscriptions are unavailable, the Structure view says automatic source updates are unavailable and asks for Refresh; explicit Refresh starts a new source pass, clears old diagram selection/models and rewarms the applicability/live caches. State changes and watched invalidation also notify an open packaged page with a model-free `ui-kit-refresh` that carries no source data.

## Not implemented

- The Kotlin DSL; SpEL beyond the strict literal checks; adapter-specific attribute checks (JMS, AMQP, HTTP…); DSL flow chain edges in the diagram.
- Constants in channel names; beans and channels from libraries, auto-configuration or other modules; effective runtime bean/type ownership and classpath resolution.
- Semantic (PSI-level) context/type models, cross-model usages and safe whole-model Rename; indexed Rename/Find Usages anchors for channels, jobs and modules.
- Job/module semantic indexing; typed endpoint extraction; editing existing Java/Kotlin configuration bodies; Batch job/step and Modulith module generation; queue/custom channel creation options; runtime job controls outside the reviewed CLI profile.
- Native graph layout, keyboard/scroll behavior and theme acceptance of the packaged graphs.
